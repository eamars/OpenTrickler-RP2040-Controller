### The nine other makes, as the code has them

The draft plans one reader that takes "a frame at its line ending (the make says which)". Read in `src/drivers/scale_protocols`:
- **At a line ending:** the Sartorius, the FA-E/EN and the Generic. None checks a length.
- **By a count of bytes since the last LF, published at the count, before the line ends:** the Steinberg, the Creedmoor, the G&G, the US Solid, and the Radwag (which also checks its frame starts "SUI"). A byte too many, or a task resumed in mid-frame with its old count, is read as a frame from the wrong place. This is the stitched frame ADR-013 found on the A&D, still there in five makes.
- **By a header byte and 17 bytes:** the JM Science. No line ending at all.
- **Asked for:** the G&G sends a request every 250 ms and reads the answer. "A make is a parser and its zero command, with no task" has no place for that.
- **The Generic** parses the tail of any frame longer than 31 bytes as a frame of its own (`generic_scale.c:72-75`): "...  12" then "3.45 g" reads 3.45.

So a make must say how its frame is found (an ending, a count, or a header and a count) and whether it is asked for. That is still one reader and a table, but it is not the design in the draft.

### Is anything handed on missing?

The five items of ADR-006's README and the two found on the way are all there. Missing, each found in the code:
1. **The settings' mender** (finding 2): a second place where the start writes over a stored value.
2. **A save cut by the power.** A record is written a 64-byte page at a time, 5 ms each (`cat24c256_eeprom.c:39-58`); the powders' record is ten pages. Power lost between pages leaves new pages, old pages and the old CRC: at the next start it matches at no size and the defaults are written. Both the old and the new settings are gone, the calibration with them.
3. **A write believed on its address alone.** `chip_i2c_write` (`chip_i2c_rp2.c:27`) takes anything but "no answer" as done, a write the chip stopped acknowledging part-way included, and nothing reads a record back.
4. **A held write that fails is dropped.** At an update's confirmation, a record that does not write is printed and freed (`common.c:194-200`): the settings changed on the trial are lost with no word on the screen.
5. **The erase's two other holes.** The lock must be held until the chip restarts, or a save between the last page and the restart survives a factory reset. And the erase is the one write that goes round a trial's hold: a factory reset asked while an image is on trial erases the EEPROM, the trial then goes back, and the image it goes back to finds nothing (the API refuses it during a job, not during a trial; `api_v1_commands.c:1685-1704`).
6. **The storage's memory on the Pico W.** The loader's buffers and a trial's held records come from the C heap, which on the Pico W is 3,492 bytes in all (`build_adr006/g10_w/app.elf.map`: `__end__` to `__HeapLimit`). The worst case today is about 2.2 KB by my sum (not measured). The SDK's `malloc` panics when it runs out, and a panic enters the USB loader: a dead-looking unit at its start. Every static byte ADR-014 adds comes out of that heap.

Nothing in the draft is out of place. "Not in this ADR" is right.

### Root fixes, or guards?

**Gate 1 is five guards where one rule is broken.** Today a load that cannot use what is stored destroys it, and a module whose load fails does not start. The rule to build:

> A load never writes, and never stops a module from starting. It leaves the module usable, on its defaults, and says what it found: read, read from another version, blank, damaged, or not reachable. Only a save the user asked for writes.

- **One mechanism, already in the tree.** An update's trial does exactly this: writes are held in RAM, a record that did not read is "held as its defaults", and the unit says which settings were reset (`common.c:146-214`). Off a trial the same hold serves. No second mechanism.
- **It makes the absent EEPROM the same case** as the damaged record: every record "not reachable", every module started, the screen alive to say so. The NULL calls go because no start returns early, not because each is guarded.
- **It covers the mender**, and names the two migrations the start does write on purpose (the motors' current, the display's rotation).
- **"Read again before anything is decided" is a guard**, and as written it would not even work: the loader already reads the slot a second time and skips the record's own size (`common.c:328`). The root form: read the slot once and check every size from that one buffer; on no match read it once more and compare. The two reads differ: the bus is at fault, say that. They agree: the chip holds damage, say that.
- **Blank is not damaged.** A new unit, a slot a new record takes (ADR-014's), and the EEPROM after an erase all fail the CRC. They must stay silent, defaults stored, as today. The draft does not draw the line; first two bytes `0xFFFF` is where it is.
- **The I2C time limit** is a change to a platform interface. Gate 7's own rule applies: the call's ESP-IDF counterpart read first (its I2C calls take a timeout already), written in `chip_i2c.h`.

**Gate 2 is a root fix** (one way to find a frame in place of ten), provided the design covers the makes as they are.

### The gates, their order, the proofs

- **Two gates in one ADR, storage first:** right.
- **Gate 1's proofs are real** but for one. The test build with the EEPROM at an address no chip answers, and the one that reads a record with a failing CRC, would each expose the failure. **The time limit has no proof:** a chip that does not answer returns at once, so that build never reaches it. A test build that holds SDA low by a plain output before the read does.
- **The filler tool** needs v1.21's layout from a compiler once, not in every CI run: read it from a v1.21 build, keep it as a table in the test, and compare CI's own ELF with it. Written to take any ELF, it is also the check ADR-007 asks for ("every record's size and offsets, by both").
- **Gate 2's proof for nine makes is weak.** Frames typed from a manual are the author's reading of that manual, which is what the parser was written from. Stronger, and it needs no scale: build each make's task as it is today on the PC over a fed serial port (gate 10 did this for the Generic), feed the old code and the new reader the same streams, whole frames, cut frames, a byte dropped, a byte added, and require the same readings but for the faults the gate means to fix, each listed. Gate 5 proved the ring that way.

### To settle before approval: my answer to each

1. **The order.** Agreed: next after ADR-006. Gate 1 before ADR-014, which adds a stored record and, if the last weight is kept with a charge profile, a save at every change of weight. Both gates before ADR-007: its EEPROM lands on pins the draft of ADR-007 calls "not confirmed", so its first start may well meet an EEPROM that does not answer, and one reader is one user of its serial driver.
2. **A record that fails its CRC.** Agreed with the draft: run on the defaults, unwritten, and say so. Two conditions: blank stays silent, and the damaged bytes stay on the chip until the user saves that module or resets it, so a copy can still be taken. I would not refuse a charge for a damaged record: a new unit runs on the same defaults, and what is lost is the tuning, which is what the notice is for.
3. **An EEPROM that does not answer.** Agreed: the menu and the console, a charge and a calibration refused, the screen saying why, as a missing scale does. Here refusing is right where for one damaged record it is not: nothing set can be kept, and nothing can be mended from the unit.
4. **One ADR or two.** One, two gates.

### With ADR-007 and ADR-014

- **ADR-014:** a new record must start with two zero bytes, take a slot of 13 to 20 KB and clear it first, join `release_records.py` and the update's reset bits (ten of sixteen used, `update.c:239-250`), and fit the Pico W's C heap (above). None of this is written where ADR-014's author will meet it.
- **ADR-007:** the one reader should read with a wait (`chip_serial_read_within`), not poll every 20 ms: ESP-IDF's driver hands bytes over late, and on the RP chips a 32-byte FIFO polled every 20 ms overruns above some 1,600 bytes a second (19,200 baud streams 1,920; no make is known to stream that hard, not measured).
