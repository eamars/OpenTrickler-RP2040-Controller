# Working on this repository

Firmware for the OpenTrickler controller: a Raspberry Pi Pico W or Pico 2 W on the motor expansion board, with a mini 12864 display and rotary encoder, two TMC2209 stepper drivers, two servos, LEDs, an EEPROM and a scale on a serial port (see [README](README.md)). The trickler dispenses gunpowder. This page is for anyone, person or agent, about to change the firmware.

## Before anything: fetch

Run `git fetch` and compare your `main` with `origin/main` before you read the code as current. A checkout can be months behind. The first plans for this repository were drafted against a `main` that was 11 commits old, and had to be corrected.

## Build, flash

- **Clone** with the submodules: `git submodule update --init --recursive`. `library/` holds the Pico SDK, FreeRTOS and LVGL.
- **Toolchain:** every version is written once, in `toolchain.env`: the compiler, CMake, Ninja, `pioasm` and picotool, OpenOCD. The scripts below and CI read it; change a version there and nowhere else.
  - Windows: `setup_toolchain.ps1` fetches them into `%USERPROFILE%\.pico-sdk`, and `configure_env.ps1` puts them on the path. The VS Code Pico extension makes the same folder (README). `-List` prints what it would fetch.
  - Linux (what CI runs): `setup_toolchain.sh` fetches the same set into `.toolchain/` in the repository, and `source ./configure_env.sh` puts it on the path.
  - macOS is parked (the owner, 2026-11-14: development is on Windows, integration builds on Linux). Its scripts as last used are in git: `git show 2ad9b0a:setup_toolchain.sh` and `configure_env.sh`. They come back when the owner works on a Mac again.
- **Build:**
  - `.\build_pico_2w.ps1` builds the Pico 2 W image into `build\`;
  - `.\build_pico_w.ps1` builds the Pico W image and its bootloader into `build_w\`.
  - Both run CMake's configure each time, so a new or removed source file is picked up (sources are found by a glob), and the image's metadata block carries this commit's version (ADR-004: it is taken at configure time).
  - **What a build carries** (ADR-008, gate 2): a part a build may leave out is a CMake option, on by default on both boards, printed as it configures (`Features: ...`), and reported by the unit in the index's `features`. Today `-DFEATURE_SERVO_GATE=OFF` (the LEDs cannot be left out: they light the 12864's backlight). A page's rows are counted from their list (`ROW_COUNT`), never by hand: a row left out of a build overran a count written by hand.
  - **The flash layout** (ADR-004): two image slots on each board, `targets/flash_layout.cmake`. The Pico 2 W's ROM keeps them by its partition table (`targets/pico2_w_partition_table.json`); the Pico W has our bootloader (`bootloader/bootloader.c`) at the start of flash, and its image is linked for one slot (`-DAPP_SLOT=A|B`, A by default). Each build makes `full_install.uf2`, the file for the USB drive. An update image is built with `-DAPP_TRIAL_IMAGE=ON`.
  - **A release:** `python scripts/build_release.py` makes its five builds into `build_release\` and its files into `release\` (the full installs and the update images, each named `OpenTrickler-<version>-...`; `manifest.json`, `SHA256SUMS`). CI runs the same on every build and keeps `release\` as an artifact.
  - **A release's tag** is `vX.Y.Z`; its build reports `X.Y.Z`, a build N commits after it `X.Y.Z-N`. Its notes are written first, in `docs/releases/` (its README gives the steps, as the Open Weapon Mount Computer's). CI on the tag runs `build_release.py --tag`, which refuses a firmware that does not report the tag and a tag without its notes, and gives each file its address on the release; it then drafts a pre-release, which the owner publishes after trying it. Until every ADR is closed every release is a candidate, a pre-release, with no install steps given (the owner, ADR-004).
  - `src/generated/` is made by the build (version, pages) and is not tracked. PIO headers go to each board's build folder (`build\src\`, `build_w\src\`): pioasm writes a different one for each chip, and a shared one broke the Pico W image (ADR-001, F7).
- **The charge's fixed numbers are in one file, `src/charge_rules.h`** (ADR-009, gate N): every share, count, bound and wait the charge and its controller use, each a macro with its unit, what it is for and its row in the ADR's `numbers.md`. A build with another value changes it there and nowhere else. `venv\Scripts\python tools\charge_sim\check_numbers.py` fails on a number written into the charge's files (`charge_control`, `charge_calibration`, `charge_mode`) and on a macro with no row; CI runs it. A number added to the controller gets its macro and its row in the same commit.
- **Size:** `python tools/size_report.py build/app.elf.map --bin build/app.bin` prints the image's flash by part and the RAM taken at link time. An image larger than its slot fails to link (`region FLASH overflowed`). The first remedy is third-party code at `-Os` in every build: the owner chose that for LVGL and mbedTLS in ADR-010, and `sha256.c` is at `-O2`. Our own code stays at `-O0`, for debugging, but for the API's JSON writers (`recording.c`, `api_v1_commands.c`, `settings.c`), at `-Os` since ADR-009's gate 2 at the owner's word, when the Pico W's image had 1,088 B of its slot left (21.6 KB after). The next remedy is ADR-005's optimised build, and only then is anything cut. (The Pico W's image was 799 KB, 583 KB at `-Os`, 2026-11-17; 980 KB with ADR-010's LVGL, TLS client and gate 6's screens, 2026-11-18.) LVGL and the TLS client are in every build: `screen` gives LVGL's heap's most, `update poll` what the last fetch took (its handshakes, mbedTLS's peak, the heap's low mark, its task's stack), and `stats tasks` each task's stack never touched. CI prints the same for both boards on every build, in the job summary and in the log (`gh run view <id> --log`).
- **CI builds with what a PC builds with.** It runs on `ubuntu-latest` but uses none of the runner's compiler or tools: `setup_toolchain.sh` fetches the set `toolchain.env` names, kept in GitHub's cache until a version in the file changes (ADR-011). A new runner image does not change the build. CI's image is about 1.3 KB larger than a PC's, and that is all paths: each assert stores its source file's full path, and CI's checkout path is 35 characters longer than `C:/workspace/OpenTrickler-RP2040-Controller` (37 paths in the Pico W image, 34 in the Pico 2 W's; measured 2026-11-14).
- **Flash:**
  - **With a debug probe on the unit's SWD port** (the bench): `venv\Scripts\python tools\remote_control\rc_run.py flash`. It is the full install through the probe: the whole flash erased, then what starts it (the partition table or the bootloader) and the image's `.bin` in slot A; it verifies each write and passes when the unit's console reports the build's version. This is also how the bench's unit is recovered, from an assert or a hard fault too.
  - **By hand**, as a user does: hold BOOTSEL, plug in USB, copy `full_install.uf2` to the drive ([manual](manuals/firmware_update_via_usb.md)). There is no going back to an older version (the owner, ADR-004).
  - **Over Wi-Fi** (ADR-004), through the API only, for debugging, until the web UI and the screens offer it: `rc_run.py update --host <address> --manifest release\manifest.json`, or a release's manifest by its address. In a test, the manifest comes from disk or from the local OTA server, never from GitHub's releases (the bench rules, below).
- **Host tools:** Python from the venv at the repo root (`venv/`, built from `requirements.txt`). Never a second venv.
- **The unit's API from Python:** `tools/remote_control/unit_api.py` works from what the unit says of itself (`GET /api/v1` and its schema), checks a write against the schema before sending it, and follows the event log. `python tools/remote_control/unit_api.py <address>` prints what the unit is, its paths and its actions.
- **Say hello** (the owner's mode for agents, for fun, 2026-11-17): an agent tapping into a unit over the API may `POST /api/v1/agent/hello` with `{"name": "<who you are>"}` (printable ASCII, 1 to 16 characters; `{}` is Claude-chan). The screen shows Claude-chan rising at the bottom right, a round bubble over her saying "<name> is watching ya!", for 2 s, the whole panel flashing first when no agent has said hello for 10 minutes. Refused with 409 while a charge runs: a charge's screen is never covered. Over every other page and job (a purge, an update) it plays, and the reset button still stops the job under it (the owner, 2026-11-17). Listed since ADR-008's gate 2, in the index and the schema (an action of the kind `agent`; its GET gives its usage). The bench rules hold for it as for any call, and it is not sent while a tour or a test reads the screen.
- **Screen work without a unit:** `venv\Scripts\python tools\ui_mock\menu_12864.py` draws gate 4's screens of the menu, the faces and grid every mock uses, with the screen's own fonts (`fonts/`) at the panel's 128 x 64, onto one sheet (`docs/developments_plans/ADR-010-lvgl/mockups/`); `tools\ui_mock\parity_12864.py` draws the menu as gate 6 built it (every setting the unit needs, on both the screen and the web) onto `parity_12864.png`. `tools\ui_mock\panel.py glyphs <font> <characters>` prints a font's glyphs. The skill `embedded-ui-design` says how a screen is designed.
- **Page work without a unit:** `venv\Scripts\python tests\web_test.py` serves the portal as `scripts/web_build.py` builds it (`build_web/`) at the unit's own addresses, and a recording of a unit's replies (`tests/web_test_data.json`), at http://127.0.0.1:8000/, checking each write with the client's code; `--hotspot` starts it as a unit never set up, on its own hotspot. `--record <address>` records a unit again when the API grows; the owner's Wi-Fi name, the unit's address and the networks heard are left out before it is written.

**Settings in the EEPROM:**
- Each module stores one struct in its own 1 KB slot with `load_config` and `save_config` (`common.h`), with a CRC32.
- The struct's layout is the stored format. A change that alters its size resets that module's settings to their defaults on every unit. **A field that fits in the struct's filler does not:** the size stays, the old record passes its CRC, and the new field reads whatever byte was stored there (ADR-006, handed on by ADR-010). Check the size before and after (`arm-none-eabi-gdb -batch -ex "p sizeof(<type>)" build_w/app.elf`).
- Never change a stored struct's layout without saying so in the ADR.
- **Each setting is described once,** in its module's table (`settings.h`; charge mode's and the display's in a C file beside their C++ one): name, type, unit, limits or choices, when it applies, a line on what it is, and where it lies in the struct. A new setting goes in the struct and the table, and the API, the export, the schema, the portal's form (by its field's name) and the console's `setting` follow. `saved` is the struct's CRC against what was last stored, so a write from the menu counts; for a resource that shares its record (a powder of the eight, a motor of the two) it is its own part against what the EEPROM holds of it, read only when the record is not stored (ADR-008, gate 2). Each resource names where its part lies in the EEPROM (`addr`) and its revert (`revert_path`).

**Style:** the skills in `.agents/skills`:
- `c-style` for all C and C++;
- `py-style` and `python-venv` for host tools;
- `embedded-ui-design` for anything on the unit's screen: its fonts, grid, kinds of screen and wording, and mock-ups before code.
- `web-ui-design` for anything on the web pages (ADR-008): layout by width, targets for gloved fingers, colour only where it means something, forms, confirmations, the captive-portal sheet; the mock on the stand-in before the unit.

## Proving a change on a unit

Changes are proven on a real unit, not only built. The usual proof, after a build: `rc_run.py flash`, then `rc_run.py menu_tour --compare tests/menu_baseline/<board>` (the unit's own), then `rc_run.py charge_cycle`. Each must end `VERDICT PASS`. A change meant to alter a screen updates the baseline in the same commit, with `--save`.

- **One unit is enough for a change in the application layer** (the owner, 2026-11-15: "We don't need to repeat on Pico W for application layer changes"). Read here as:
  - a change that touches nothing the two boards differ in (the modes, the control loop, the menu's logic, the profiles) is proven on whichever unit is on the probe;
  - a change to a driver, the PIO, timing against the chip, memory, the network or the build is proven on both;
  - except memory and the network once they are proven on the Pico W, the tighter of the two in RAM and speed (the owner, 2026-11-17, skipping the Pico 2 W's run of ADR-010's gate 5: "If we have verified the function on Pico W then Pico 2W is lower risk target"). Code of the RP2350's own (its slots, its PIO, its timing) is still proven on the Pico 2 W.

- **The bench rules** hold for every way of reaching a unit, the tools below included:
  - No contact with the hardware (no flashing, no serial port, no debug probe, no call to a unit over the network) until the owner says the bench is ready. Ask again in every new session.
  - An agent's run assumes the hopper is empty. The owner says when there is powder in it.
  - The motors may turn in an agent's run.
  - **The cup is checked by the tools** (the owner, 2026-11-23: the hopper stays filled). A simulated charge, a purge and `pulses` pour real powder. Every `rc_run.py` command that can turn a motor, and `tools/charge_sim/bench/robust_staged.py`, reads the real scale first, refuses a run whose most pour would take the cup past 600 gr (`VERDICT FAIL cup: ...`), reads it again after, and writes both into `logs/adr009/cup_ledger.csv`. Each run's most is computed from its motors' bounds at 12 gr a turn (`cup_most` in `rc_run.py`; `pulses` 372 gr), and the ledger says what each run really poured against it, `--most-pour` overrides it, and `--no-cup-check <reason>` runs with no reading, logged. A new command that turns a motor gets its most in the same commit.
  - **A debug image goes onto a unit by the probe** (`rc_run.py flash`), never by an update (the owner, 2026-11-17).
  - **An update test never fetches from GitHub's releases** (the owner, 2026-11-17: they are not to be hammered). The unit's poll and download, and `rc_run.py update`, take their manifest and image from a local OTA server on the PC.
    - **That server is `tools/ota_server.py`.** Run `--make-certs --host <this PC's address>` once; it then serves `logs/ota_server/releases/<tag>/` (one release folder each) in GitHub's layout:
      - over HTTP (8080) and HTTPS (8443);
      - each download redirected to an asset host (8081 and 8444), with test chains of GitHub's two kinds;
      - every request printed.
      - GitHub's list of releases, `/api/v3/repos/<owner>/<repo>/releases`, for the beta channel; a release folder holding a file named `prerelease` is a pre-release, listed but never the latest.
    - **A unit trusts its test roots** only in a build that names them: `-DHTTPS_TEST_CA=ON` (ADR-010, gate 5).
    - **The server is the bench host** (ADR-010, gate 6, step 9): while it runs it announces `opentrickler-update.local` by mDNS, and every unit on the network asks it before its stored source, as the Open Weapon Mount Computer's units ask its `ota_host.py`. Nothing is set on a unit; the offer page says "From the bench host <address>". So **never leave it running while the owner tries an update from GitHub**: it takes over every unit's poll. `--no-announce` serves without the name, for a unit pointed at it by its stored source.
    - **The bench's units also store the local OTA server as their update source** (`setting settings/update source=http://<this PC>:8080/a/b`, then `save`), so a start with the server stopped still never polls GitHub. A factory reset puts GitHub's back: store it again.
    - **The test releases of ADR-010's gate 5** (v9.0.0, which confirms itself, and v9.0.1, a pre-release that never does) are kept in `logs/adr010/gate5_releases/`, out of the served folder: served, every unit would be offered them and its main menu would differ from its baseline.
- **The bench** (2026-11-14): a Pico W on the motor board with an A&D FX-300i scale, reached only by a Raspberry Pi debugprobe on SWD. Its USB port is not connected.
  - A second unit, a Pico 2 W on a controller board of its own, with its own EEPROM and so its own settings, is put on the probe when the owner is asked. One unit at a time. `rc_run.py --board pico2_w` drives it. Its menu baseline was saved whole on 2026-11-19 (ADR-008), which was ADR-010's last check on it: compare against it, and save it again only with a change meant to alter a screen.
  - The bench's unit has no servo gate fitted. The day one is, ADR-010's other last check: the servo seen moving to a shutter's end from Settings › Servo gate.
  - The A&D goes to whichever unit the owner connects it to. `state` tells: a number when a scale sends, `nan` (`inf` on the Pico W, whose float code treats NaN as infinity) when none does. Charges in proofs use the simulated scale either way.
  - Each unit is on the owner's Wi-Fi with an address of its own, given by DHCP: ask, or read it from the unit's screen.
- **The web has little memory.** A socket copies every byte it sends into lwIP's heap and holds it there until the client acknowledges it, and so does every TCP connection lwIP keeps, those the server has closed included. So the heap (40,960 bytes) is sized for lwIP's 12 connections with a send buffer of 2 segments each, and taken from the FreeRTOS heap (112 KB). On lwIP's own file server the Pico examples' 4,000 bytes ran out 7,404 times in a ten-minute soak and missed 8.9% of the web's reads (ADR-003, gate 1); on sockets, 16 KB ran out 340 times under a tuning session's load, 24 KB 54 times (gate 2). The most used moves with the Wi-Fi. A change to the server is soaked, with `--load` where it touches what a stream sends, and `net` says what it takes.
- **A GET changes nothing** (api_v1.md): read a unit over the web freely. A unit with a firmware from before ADR-003's gate 4 still has the old `/rest/` paths, which do change it (a GET of `/rest/profile_config?pf=N` selects profile N): read such a unit through the console, and copy its settings with an `rc_run.py` of its own time (below).
- **Flashing a unit can reset its settings.** When a stored struct's layout differs from the one on the unit, the defaults are written at once (`common.c`). Copy the unit's settings before the first flash of a newer or older version.
- **The console** (ADR-001, step 3) is stdio over RTT: the debug probe reads it from the chip's RAM, with no pin and no cable to the unit. Lines starting with `@` belong to the remote control; everything else is the firmware's log.
- **`tools/remote_control/rc_run.py`** (run with the venv's Python) starts openocd itself, keeps each session in `logs/rc/`, and ends with `VERDICT PASS` or `VERDICT FAIL <reasons>`, exiting 0 or 1. It does not start while another openocd holds its Tcl port, which would take its commands; a run that raises fails with its traceback in the log and stops its openocd:
  - `send "state" "stats"`: commands, one after another (`help` lists them). `pause <seconds>` between them waits on the PC, for a command whose work outlasts its reply;
  - `flash [--elf <path>]`: write, verify, start, check the version;
  - `reset`: a whole-chip reset by the watchdog (openocd's own `reset run` locked the RP2040 up, F8);
  - `watch <seconds>`: log the console for a time;
  - `snap`: the screen as a PNG under `logs/rc/snaps/`, as a person at the unit sees it;
  - `menu_tour [--save <folder>] [--compare <folder>]`: every page of the menu in turn, opened by its id (`page_<id>.png`), pressing nothing; it first waits for the marks every title shows to settle (the remote mark gone, the Wi-Fi's shown). The baselines are `tests/menu_baseline/pico_w/` and `tests/menu_baseline/pico2_w/` (each unit's own settings: the Pico W's display is stored upside down). The Pico 2 W's pictures removed after ADR-010's gate 5 (the Wi-Fi icon, the offer page) were saved again on 2026-11-19 (ADR-008). Compare against the unit's own to see what a change did to the menu. The set-up's code (`setup`) is snapped into the session's folder only, never a baseline, and not compared: it is the unit's hotspot key (ADR-008, gate 4).
  - `reach`: every element of every screen reached by turning alone (ADR-010, gate 6): each page by its id, each screen a row opens (a click, then Back), the dialogs, a simulated charge's screen while it zeroes and between throws (then the page its Change opens), and a cleanup's at speed 0, each turned to its top and down a detent at a time. It fails on a "<" title, a row that acts, a notes' button, a softkey or a digit of the target never reached. It reads `screen`'s marks: `back` on `@screen` (the title is Back), `info` on a `@row` only to read;
  - `charge_cycle [--target 30]`: a charge from zero to cup return and the start of the next one, with main's simulated scale switched on for the run (`sim on`), never stored;
  - `recordings_check --host <address> [--throws 5]`: each throw of one charge read through `/api/v1/recordings/{id}/samples` and by `ccrec <id>`, row for row, its summary against its line; then a charge with `ccrec nosamples on`, which throws all the same with `samples_kept` false and 410 on its samples (ADR-009, gate 2's rest). The simulated scale, never a console series: that scale lifts its cup at every verdict;
  - `pulses`: whether the step pulses stop on a probe reset, an assert and a hard fault. All three are judged. It needs the two test images, built with `-DRC_TEST_FAULT=1` and `=2` into `build_w_fault1` and `build_w_fault2` (`build_2w_fault1` and `2` for the Pico 2 W, given with `--assert-elf` and `--hardfault-elf`);
  - `settings --host <address> [--save <folder>] [--compare <folder>] [--restore <folder>]`: `--restore` writes a copy back, each resource whole and stored, then compares (after a factory reset: the Wi-Fi's key is never in a copy, so the one stored stays; ADR-008, gate 4). Otherwise: the stored settings copied over the web API (`GET /api/v1/settings`, which changes nothing) and compared with an earlier copy, a field at a time; the firmware's version is reported, not judged. Take one before every flash of another version. Copies made before ADR-003's gate 3 are of the old paths and do not compare: the Pico W's v1 copy is `logs/adr003/picow/before_gate3_v1/`. A unit still on such a firmware is copied with the `rc_run.py` of a commit before gate 3 (`git show <commit>:tools/remote_control/rc_run.py`);
  - `api_check --host <address>`: the API by the client (`unit_api.py`): every GET path the index lists read twice, each answer checked against the schema's tables and the two the same, the settings and the event log unchanged; then every action the schema lists called where it is safe, each answered as api_v1.md says, a charge and a purge started and stopped with their events (the simulated scale on for it), and last a restart, after which the boot is new. It fails on an action it did not call (ADR-003, gate 4);
  - `stream_check --host <address>`: the event stream's life cycle (ADR-008, gate 2), stage by stage: its start (the unit, then the state), an event with its id, a reconnect from its last id with nothing missed, one whose event is no longer kept read afresh, the live weight within a second, the state again after 15 s quiet, the cap (a fourth refused 503 with `Retry-After`), a client that stops reading closed by the stall limit with lwIP's heap given back, a Wi-Fi leave and a restart (the leave leaves the old stream silent, the restart closes it; the reconnect goes on after the leave and starts afresh after the restart). It restarts the unit;
  - `settings_roundtrip --host <address>`: every setting written back as read and read again, unchanged; each field given a value outside its limits, refused, the resource unchanged; a write to the charge's and the motors' settings during a throw refused with 409. Nothing on the unit changes (ADR-003, gate 3);
  - `soak <seconds> --host <address>`: charges back to back with the simulated scale while two browsers use the web pages (the mirror, the charge page's polling, the portal reloaded, the settings read). It fails on a failed charge, on memory that is not given back (the FreeRTOS heap read quiet before and after), on an allocation lwIP's heap or a pool failed during the run (`net`, read at its start and end), on a late feed of the step pulses (`motor`), and on web reads missed past `--max-miss-share` and `--max-miss-run`; it sums the misses by kind (timeout, reset, refused, wrong). It is not part of every proof: whether a change needs one, how long, and against what limits is decided for that change, for the area it touches. Its web figures compare only when nothing else uses the unit's web pages: a browser left open on the unit tripled the timeouts of ADR-011's step-3 soak. Each poller's reply times are given (median, 95%, longest). `--load` adds what a tuning session asks of the unit: a reply the size of a throw's samples (600 rows of 16 numbers, `/api/v1/debug/load`) pulled back to back, a client reading the charge four times a second, and a client pulling each throw's recording whole as it completes (ADR-009). `--stream` has each browser follow the event stream (ADR-008, gate 2) in place of polling the charge, each judged as a follower is: every event, no gap, no reconnect read afresh. `--upload` adds ADR-004's image: 700 KB sent back to back as a body taken in pieces (`PUT /api/v1/debug/upload`), each checked by its CRC-32. Two clients follow the event log with held reads through every soak, and it fails when either misses an event or they differ;
  - `web_robust --host <address>`: requests that are wrong or awkward (headers of 8 KB, a request line too long, another `Host`, a body longer than it says, a chunked body, a client that stops reading, writes that are not JSON or not the resource's...), each answered or closed as api_v1.md says, then seven clients at once, the parked requests and two stalls; the unit must go on answering after each (ADR-003, gates 2 and 3);
  - `scale_frames [--idle s] [--handovers n] [--reboots n] [--motors s]`: the scale's frames through the tap, summed up by phase: how many read as a number, the texts of those that did not, the time between frames (ADR-013);
  - `charge_fault <bad|quiet|purge|none> --host <address> --expect seen|not-seen`: a simulated charge with one fault put in at a weight, `state` read every 50 ms, and the charge's own `Charge: ...` lines checked with `--want` and `--want-none` (ADR-013).
  - `slot_trial --image <elf> --expect confirmed|back|refused [--corrupt]`: an image written into the free slot through the probe and tried (`update try`), no network (ADR-004, gate 1). The session's `--elf` is the image the unit runs, its update image's is `--image`: each image's console is found where its own ELF says;
  - `update --host <address> --manifest <manifest.json> [--expect confirmed|back|refused|cut|busy|second] [--refused-code <code>] [--browsers] [--new-elf <elf>]`: an update through the API from a release's manifest, the unit followed through its restart and judged by the image sent; `back` also has a start during the trial refused, `second` a second upload while the first is open; `power-upload` and `power-trial` cut the power by the probe (both cores halted, the scratch registers a power cut clears set to zero, the chip restarted) half-way through the upload, or while the image sent runs on trial, which must be one that never confirms itself; `--browsers` has two browsers on the pages during the upload (ADR-004, gate 2). Test images: `-DRC_TEST_BLOCK_VERSION=<first;second>` (a block version of its own), `-DRC_TEST_NO_CONFIRM=ON` (never confirms), `-DRC_TEST_HANG_AT_START=ON` (hangs at its first line: only the boot's own watchdog ends its trial), `-DRC_TEST_WIFI_FIRST_JOIN_FAILS=ON` (the start's Wi-Fi join skipped).
- Console commands to drive the menu (ADR-010): `press <cw|ccw|enc|rst> [n]` (`enc` a click, `rst` Back; no long press); `screen` (what is on screen, in words: its id, kind (list, dialog, notes, edit, job, control, code), title, focus and marks (`back` when the title is Back), then a list's `@row` lines (`opens`, `editing`, `chosen` for a choice's current option, `info` for a row only to read), a card's, a dialog's or notes' `@line` lines and `@button`, the code's `@code` text (the set-up's: the hotspot's name and key) and its lines, the editor's or a job's `@figure` line (`editing` while a digit is being set), and `@softkeys` (`focus=left|right`, the one a click does); its reply gives LVGL's heap, the most used and the least free in one piece since the start), `screen list` (every page's id) and `screen <id>` (open a page, pressing nothing). `knob`: the knob's tap, taken and cleared: every edge of its button (`d` a press taken, `u` its release, `X` and `x` a bounce dropped) and each turn sent (`r`, `l`), with its time in microseconds, and `q` for an event the menu's queue had no room for.
- Console command for the settings (ADR-003, gate 3): `setting` lists the resources; `setting <path>` gives each field as an `@setting name=value` line; `setting <path> name=value ...` writes first, through the same tables, checks and refusals as the API (`@err <code> <field> <message>`); `setting <path> save` stores it, `setting <path> revert` puts back what is stored (ADR-008, gate 2). The path as the API's, with or without `/api/v1/` (`setting settings/charge`, `setting powder_profiles/3`). A write is live, not stored, until saved; the Wi-Fi key is written but never shown.
- Console command for the network (ADR-003): `net`, lwIP's heap and the pools a web connection takes from (TCP connections, segments, pbufs, receive buffers), each in use, most ever, size and failed allocations, and the event streams open, opened and refused (`live`, `live_opened`, `live_refused`; ADR-008, gate 2). The heap is 40,960 bytes (ADR-003, gate 2); a change to the server is measured with it. `tcp_pcb` at 12 of 12 is no fault: closed connections wait out TIME_WAIT there and lwIP takes back the oldest for a new one, counting a failure only when none can be taken (`tcp_alloc`). `GET /api/v1/debug` gives the same over the web, with the server's own counts. `net log on|off` (never stored) puts each connection and request on the console, with the client's address and the unit's time: a client's link read by its own reads (ADR-008, gate 4). Always on the console: each reply of 400 or more in the unit's own words, a request dropped or reset, and the slots all held.
- Console commands for updates (ADR-004): `update` (the slot running, whether on trial, the free slot, the job), `update try` (a trial of the free slot's image, once it is checked), `wifi leave` (the station leaves its network, as when its router goes away; it joins again within a minute). `wifi scan` (the set-up's scan, waited for: `@scan` lines, each network by name, strongest first) and `wifi join` (the stored network with its stored key, through the set-up's join: only while the unit is its own hotspot, which stays up; the end in `GET /api/v1/network`'s `station`) (ADR-008, gate 4). A probe build, `-DRC_TEST_AP_PROBE=ON` (ADR-008, gate 1), starts as its own access point and never retries its network by itself. ADR-010's poll: `update check` (a poll now), `update poll` (how the last poll went, and what its fetch took). A download logs what it took (`Update: downloaded ...`) and the job task's stack at install, before the restart wipes them.
- Console command for the tasks: `stats tasks` gives each task's stack never touched (`@task` lines) before the `stats` reply. The job task's and the poll's stacks were sized from it (ADR-010, gate 5).
- Console commands for the motors and charging: `motor <coarse|fine> <rev/s> [<seconds>]` (the run stops by itself after its seconds, 15 by default, 120 at most: nothing a test starts turns a motor without a bound, ADR-009 gate F.1), `motor` alone (the steps counted on each STEP pin, the steps fed, the feeds that came late, with the unit's clock: two replies give a speed), `sim on|off`, `charge <gr>` (a start through the same entry point as the API's, `by` console), `charge stop`. `ccrec [<recording>]` (a throw's rows as its recording holds them), `ccrec nosamples on|off` (never stored: the next charges' samples not had, as when the Pico W's heap cannot give them).
- Console commands for the motor drivers (ADR-012): `tmc <coarse|fine>` (the driver's registers by field as `@tmc` lines, then its serial line's counts), `tmc <coarse|fine> setup <n>` (set up n times from the stored settings), and, never stored, `tmc <coarse|fine> lose` and `find` (the driver made to look absent, and found again) and `tmc <coarse|fine> fault <short|hot|reset|supply|none>` (the driver read to report a fault). `state` ends with `drivers=<coarse>,<fine>`: what each driver was last found to be.
- Console commands for the scale, never stored (ADR-013): `scale tap on|off` (the A&D driver's frames as `@sf` lines), `sim bad` (the simulated scale's next reading does not parse), `sim quiet <ms>` (it sends nothing for that long), `sim rate <per second>`, `sim weight <a number|off>` (it shows that weight, whatever its powder does); since ADR-009's gate F.1, `sim flow <share>` (the share of what the tubes turn out that lands: 0 an empty hopper, 0.333 a tube pouring a third) and `sim offset <a number>` (added to every reading: a drift, a push), both put back by `sim off`. `stats` counts `bad_frames`.
- It counts as failures: a line with `assertion` or `PANIC`, no reply within 5 s, an `@err` reply, `up=` going backwards unasked, and a core found halted (named with its function).

## Decisions and ADRs

Work is planned and recorded as architecture decision records in [docs/developments_plans](docs/developments_plans/README.md). The process is in that README. The parts that trip people up:
- **Approval first:** an ADR is approved by the owner before work starts.
- **One at a time:** one ADR is open at a time; a functional change and a dependency update are never mixed in one.
- **Plain form:** plain words. What we want, the owner's direction, what we know (measured or checked in the code), what we do, how the unit shows it works. `progress.md` records what was built and measured.
- **Close before the PR:** an ADR is closed (Built, in its README, its progress and the index) in its branch before its PR is opened.
- **Stage gates, not small ADRs** (the owner, 2026-11-15: "Don't use small ADR. If you need staged release, you can have smaller stage gates within ADR-003"). A large ADR is built in gates inside it. A gate is approved and built on its own and may be merged by a PR of its own; the ADR is then Open until its last gate, which closes it before its PR.
- **PRs from others** are not merged as they stand. Each is discussed with the owner first (ADR-002).
- **A change to the ADRs goes straight to main** (the owner, 2026-11-17: "For ADR change you don't need PR, just merge to main directly"). Read here as: a change to the plans alone (an ADR drafted or revised, an answer of the owner's written in, the order, the handover, and the rules of this file that come with them) is committed on a branch, merged into main and pushed once, with no PR. An ADR's built work still goes by its PR.
- **An update that is not a feature may be merged without asking** (the owner, 2026-11-13: "for no feature update you can just merge the code"). Read here as: a change that leaves what the firmware does for a user as it was, such as CI, build scripts, host tools and documents. Open its PR, see its checks, merge it. A feature, or anything a user can see, waits for the owner.
- **Push only when it is needed** (the owner, 2026-11-15: GitHub has begun to block accounts that agents push from often, and the owner's must not become one). Read here as:
  - commit locally as often as the work needs; a local commit never reaches GitHub;
  - push a branch when its work is ready for its PR, or when the owner asks to see it on GitHub. Not after each commit, and not to keep work in progress safe;
  - once a PR is open, gather its fixes and push them together;
  - never push to try something in CI. CI builds with the toolchain a PC builds with, so a local build answers first.

## Do not

- **Do not edit `src/generated/`.** Change the source (a page, a `.pio` file, `scripts/gen_version.py`) and build.
- **Do not change anything under `library/`.** It is third-party code in submodules.
- **Do not change a stored struct's layout without saying so in the ADR** (see "Settings in the EEPROM").
- **Do not push often.** Push when a branch is ready for its PR, not as you go (see "Decisions and ADRs").
- **Do not merge a feature, close a PR or an issue of someone else's, or post a comment** without the owner's word. An update that is not a feature is the exception above.
