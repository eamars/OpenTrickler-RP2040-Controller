# Working on this repository

Firmware for the OpenTrickler controller: a Raspberry Pi Pico W or Pico 2 W on the motor expansion board, with a mini 12864 display and rotary encoder, two TMC2209 stepper drivers, two servos, LEDs, an EEPROM and a scale on a serial port (see [README](README.md)). The trickler dispenses gunpowder. This page is for anyone, person or agent, about to change the firmware.

## Before anything: fetch

Run `git fetch` and compare your `main` with `origin/main` before you read the code as current. A checkout can be months behind. The first plans for this repository were drafted against a `main` that was 11 commits old, and had to be corrected.

## Build, flash

- **Clone** with the submodules: `git submodule update --init --recursive`. `library/` holds the Pico SDK, FreeRTOS and LVGL.
- **Toolchain:** every version is written once, in `toolchain.env`: the compiler, CMake, Ninja, `pioasm` and picotool, OpenOCD. The scripts below and CI read it; change a version there and nowhere else.
  - Windows: `setup_toolchain.ps1` fetches them into `%USERPROFILE%\.pico-sdk`, and `configure_env.ps1` puts them on the path. The VS Code Pico extension makes the same folder (README). `-List` prints what it would fetch.
  - Linux (what CI runs): `setup_toolchain.sh` fetches the same set into `.toolchain/` in the repository, and `source ./configure_env.sh` puts it on the path.
  - macOS is parked (the owner, 2026-11-14: development is on Windows, integration builds on Linux). Its scripts as last used are in git: `git show 2ad9b0a:setup_toolchain.sh` and `configure_env.sh`. They come back when the owner works on a Mac again.
- **Build:**
  - `.\build_pico_2w.ps1` builds the Pico 2 W image into `build\`;
  - `.\build_pico_w.ps1` builds the Pico W image and its bootloader into `build_w\`.
  - Both run CMake's configure each time, so the image's metadata block carries this commit's version (ADR-004: it is taken at configure time).
  - **What a build carries** (ADR-008, gate 2; ADR-006, gate 9): a part a build may leave out is declared once, `ot_feature(<name> <module's folder> "<about>")` in `boards/common/base.cmake`: a CMake option, `FEATURE_<NAME>`, on by default on both boards; its module taken out of the board's list when it is off; printed as it configures (`Features: servo_gate=1`); and the unit's `features` in the index made from it (`ot_features.h`, in each build's own folder). Today `-DFEATURE_SERVO_GATE=OFF` (the LEDs cannot be left out: they light the 12864's backlight).
    - **Only `app/` reads `FEATURE_<NAME>`:** the start-up's wiring hands the part over or not, and the rest of the firmware asks whether it was handed, never whether it is in the build. The servo gate is handed to `services/gate` (`gate_set`); charge mode, the cleanup, the menu and the API ask the gate (`gate_present()`, `gate_enabled()`...), and with none handed each answers as a unit with no gate. A part's menu page and rows are `.shown` by its presence, its API routes, index lines and schema entries added only then. `tools/module_graph.py` fails on a switch read outside `app/`.
    - **A stored choice whose module the build does not carry runs nothing in its place** (the owner, ADR-006, gate 9): a stored make of scale the build lacks reads nothing; the start says so, `GET /api/v1/scale`'s `driver` is null, and a charge and a calibration are refused (`409 no_scale`). Before, the simulated scale could stand in while the motors poured real powder. A test build leaves the A&D's make out: `-DRC_TEST_NO_AND_FXI=ON`. **A number no make has is kept** (ADR-017, gate 1): it reads nothing at every start, shown as unknown (`null` in the API, "?" on the screen) until the person chooses a make. The settings' mender (`mend_choices`, `settings.c`) writes nothing: another stored choice no choice has runs its first choice in RAM only, its resource not stored, and a field whose module refuses such a value itself is left as it is (`unknown_kept`).
    - A page's rows are counted from their list (`ROW_COUNT`), never by hand: a row left out of a build overran a count written by hand.
  - **Modules** (ADR-006, Built; gate 3): our own code is modules, `src/<layer>/<module>/`, each a static library built by its own `CMakeLists.txt`, which makes one call: `ot_module(SRCS ... INCLUDE_DIRS ... PRIV_INCLUDE_DIRS ... REQUIRES ... PRIV_REQUIRES ...)` (`cmake/ot_module.cmake`; the arguments are ESP-IDF's `idf_component_register`, so one file will serve both platforms). It is our own function in plain CMake.
    - **A module can include only what it names.** `REQUIRES` is what its headers in `include/` include (whoever requires the module gets it too); `PRIV_REQUIRES` what only its sources do. A name is another module's, or third-party code's by ESP-IDF's name (`freertos`, `lwip`, `mbedtls`, `lvgl`), `rp2_sdk` for the Pico SDK itself, `board` for the pin map, `version` for the made version. An include of anything else fails to compile (`No such file or directory`): name what you need, or ask whether you should need it.
    - **A new source file is named in its module's `SRCS`**: nothing is found by a glob any more. A new module is a folder in its layer with its `CMakeLists.txt`, named as no other module and no ESP-IDF component is, and added to the base build's list (`src/boards/common/base.cmake`). A module's target is `ot_<name>`: what the five arguments cannot say (a file the build makes) is said with CMake's own commands after the call.
    - **A board says what its build carries:** `src/boards/<board>/board.cmake` (`-DPICO_BOARD=pico_w` or `pico2_w` picks it). Both carry the base build today, every module; the third-party code, its settings (`boards/common/settings`) and its `-Os` rule are in `boards/common/base.cmake`.
      - **A module's optimisation** is its board's: `set(OT_MODULE_OPTIONS_<module> -Os)` in `board.cmake`, after the image's own `-O0`. Neither board names one today; choose by `size_report.py`'s flash by module (ADR-005's trigger first).
      - **A place only one module can fill** (the chip's side of the platform, the screen's view) is said by the module, `ot_fills(platform)` or `ot_fills(view)` after its `ot_module()` call; a board's list with none for a place, or two, is refused as the build configures.
    - **`venv\Scripts\python tools\module_graph.py`** reads the modules' build files and prints what stands against the layers: each requirement that goes up, each loop, each module but `platform/rp2` that requires the Pico SDK, each file outside `platform/` and `boards/` that includes the SDK or the radio's driver, and each file outside `app/` that reads a part's switch (`FEATURE_<NAME>`). It ends `VERDICT PASS` since ADR-006's gate 7, and **a change must keep it there**. The file search is what holds the last: FreeRTOS's and lwIP's headers on the Pico carry the SDK's include paths, so a module that names either could include the SDK and still compile.
    - **A module never includes the Pico SDK** (ADR-006, gate 7). What it needs of the chip is a call of the platform's interfaces, each a header in `src/platform/include`, given for the RP chips by `src/platform/rp2`: `chip.h` (the time, a busy wait, the restart, the chip's id, a random number, the console), `rtos_port.h` (a task's start with its stack in bytes, a critical section, from a task or an interrupt), `chip_gpio.h` (outputs, inputs, edges), `chip_i2c.h`, `chip_serial.h`, `chip_spi.h`, `chip_leds.h`, `chip_servo.h`, `chip_net.h` (the Wi-Fi, the hotspot with its DHCP and DNS servers, the scan, mDNS), `step_pulses.h`, `update_slots.h` (the image's reading, its write, the trial's watchdog), `fault_handler.h`. A port, a bus or a strip is a number in the pin map (`raspberrypi_pico_w_config.h`). A new need of the chip is a call in the interface it belongs to, its ESP-IDF counterpart read before it is fixed (ADR-006's "How an interface is made"); a FreeRTOS call stays FreeRTOS's, but for a task's start and a critical section, whose ports differ.
    - **A module never calls a module of a layer above it** (ADR-006, gate 6). What it needs from above is handed to it at start-up, and it calls what it was handed: a struct of functions kept by its address, or a registration (`activity_set_screen`, `jobs_register`, `remote_control_register`, `api_v1_set_screen`, `menu_set_view`, `events_set_update_texts`, `update_set_fetcher`, `wireless_set_listener`, `system_before_restart`, `scale_register_make`, `fault_handler_set_stop`, `gate_set`, `charge_profiles_set_target_check`). The higher module hands it over in its own init, or `app.c`'s wiring does, which is the one place that knows every module. With nothing handed over the lower module does nothing and says so. A new console command, a new thing to end before a restart, a new make of scale: register it, do not teach the lower module its name.
    - **Another module's variable is never declared `extern`:** ask its module for a call (`scale_get_stored()`, `charge_mode_get_stored()`, `neopixel_led_default_colours()`). A hidden requirement shows in no build file.
    - Three rules the build stands on, each found by a build that failed (ADR-006's progress):
      - the image links every module whole. A plain static library loses any file linked only by its place on the link line, with no error: the hard fault's handler went that way, and the motors' stop with it;
      - a module compiles with the image's definitions, all of them;
      - **never choose an SDK option on the image alone** (`pico_enable_stdio_*`, `pico_set_*` on `app`): the SDK's libraries give a target what that target chose, and a module is a target of its own. Choose it for every target, by the SDK's global variable, before `pico_sdk_init()`.
  - **A move, or a change to how files are linked, is judged by the image's symbols:** `venv\Scripts\python tools\symbols_compare.py <before.elf> <after.elf>` compares each function and object by name and size and ends `VERDICT PASS` or `FAIL`. Our code is at `-O0`, so a file that only moved keeps every size; a function gone is a file the linker dropped.
  - **The flash layout** (ADR-004): two image slots on each board, `src/boards/common/flash_layout.cmake`. The Pico 2 W's ROM keeps them by its partition table (`src/boards/pico2_w/pico2_w_partition_table.json`); the Pico W has our bootloader (`bootloader/bootloader.c`) at the start of flash, and its image is linked for one slot (`-DAPP_SLOT=A|B`, A by default). Each build makes `full_install.uf2`, the file for the USB drive. An update image is built with `-DAPP_TRIAL_IMAGE=ON`.
  - **A release:** `python scripts/build_release.py` makes its five builds into `build_release\` and its files into `release\` (the full installs and the update images, each named `OpenTrickler-<version>-...`; `manifest.json`, `SHA256SUMS`). CI runs the same on every build and keeps `release\` as an artifact.
  - **A release's tag** is `vX.Y.Z`; its build reports `X.Y.Z`, a build N commits after it `X.Y.Z-N`. Its notes are written first, in `docs/releases/` (its README gives the steps, as the Open Weapon Mount Computer's). CI on the tag runs `build_release.py --tag`, which refuses a firmware that does not report the tag and a tag without its notes, and gives each file its address on the release; it then drafts a pre-release, which the owner publishes after trying it. Until every ADR is closed every release is a candidate, a pre-release, with no install steps given (the owner, ADR-004).
  - `src/generated/` is made by the build (version, pages) and is not tracked. PIO headers go to each board's build folder (`build\src\`, `build_w\src\`): pioasm writes a different one for each chip, and a shared one broke the Pico W image (ADR-001, F7).
- **Size:** `python tools/size_report.py build/app.elf.map --bin build/app.bin` prints the image's flash by part, our code's by module (ADR-006, gate 9), and the RAM taken at link time. An image larger than its slot fails to link (`region FLASH overflowed`). The first remedy is third-party code at `-Os` in every build: the owner chose that for LVGL and mbedTLS in ADR-010, and for lwIP, the cyw43 driver and the Pico SDK's own code in ADR-009 (2026-11-27: the Pico W's image 1,024.6 KB at their `-O0`, 10 KB past its slot, 911.6 KB after); FreeRTOS's kernel stays at the build's level, the one third-party code stepped through, and `sha256.c` is at `-O2`. The SDK's `standard_binary_info.c` stays at the build's level too: it holds the image's board, which an update checks, and at `-Os` its packed item lay on an odd byte, which a firmware before ADR-006's gate 10 does not read (the Pico 2 W refused every update image; the reader now takes it at any byte). Our own code stays at `-O0`, for debugging. The next remedy is ADR-005's optimised build, and only then is anything cut. (The Pico W's image was 799 KB, 583 KB at `-Os`, 2026-11-17; 980 KB with ADR-010's LVGL, TLS client and gate 6's screens, 2026-11-18.) LVGL and the TLS client are in every build: `screen` gives LVGL's heap's most, `update poll` what the last fetch took (its handshakes, mbedTLS's peak, the heap's low mark, its task's stack), and `stats tasks` each task's stack never touched. CI prints the same for both boards on every build, in the job summary and in the log (`gh run view <id> --log`).
- **CI builds with what a PC builds with.** It runs on `ubuntu-latest` but uses none of the runner's compiler or tools: `setup_toolchain.sh` fetches the set `toolchain.env` names, kept in GitHub's cache until a version in the file changes (ADR-011). A new runner image does not change the build. CI's image is about 1.3 KB larger than a PC's, and that is all paths: each assert stores its source file's full path, and CI's checkout path is 35 characters longer than `C:/workspace/OpenTrickler-RP2040-Controller` (37 paths in the Pico W image, 34 in the Pico 2 W's; measured 2026-11-14).
- **Flash:**
  - **With a debug probe on the unit's SWD port** (the bench): `venv\Scripts\python tools\remote_control\rc_run.py flash`. It is the full install through the probe: the whole flash erased, then what starts it (the partition table or the bootloader) and the image's `.bin` in slot A; it verifies each write and passes when the unit's console reports the build's version. This is also how the bench's unit is recovered, from an assert or a hard fault too.
  - **By hand**, as a user does: hold BOOTSEL, plug in USB, copy `full_install.uf2` to the drive ([manual](manuals/firmware_update_via_usb.md)). There is no going back to an older version (the owner, ADR-004).
  - **Over Wi-Fi** (ADR-004): a user takes the offer on the screen (Settings › Firmware) or the web page (ADR-010, gate 5; ADR-008). A test drives it through the API: `rc_run.py update --host <address> --manifest release\manifest.json`, or a release's manifest by its address. In a test, the manifest comes from disk or from the local OTA server, never from GitHub's releases (the bench rules, below).
- **Host tools:** Python from the venv at the repo root (`venv/`, built from `requirements.txt`). Never a second venv.
- **The unit's API from Python:** `tools/remote_control/unit_api.py` works from what the unit says of itself (`GET /api/v1` and its schema), checks a write against the schema before sending it, and follows the event log. `python tools/remote_control/unit_api.py <address>` prints what the unit is, its paths and its actions.
- **Say hello** (the owner's mode for agents, for fun, 2026-11-17): an agent tapping into a unit over the API may `POST /api/v1/agent/hello` with `{"name": "<who you are>"}` (printable ASCII, 1 to 16 characters; `{}` is Claude-chan). The screen shows Claude-chan rising at the bottom right, a round bubble over her saying "<name> is watching ya!", for 2 s, the whole panel flashing first when no agent has said hello for 10 minutes. Refused with 409 while a charge runs: a charge's screen is never covered. Over every other page and job (a purge, an update) it plays, and the reset button still stops the job under it (the owner, 2026-11-17). Listed since ADR-008's gate 2, in the index and the schema (an action of the kind `agent`; its GET gives its usage). The bench rules hold for it as for any call, and it is not sent while a tour or a test reads the screen.
- **Screen work without a unit:** `venv\Scripts\python tools\ui_mock\menu_12864.py` draws gate 4's screens of the menu, the faces and grid every mock uses, with the screen's own fonts (`fonts/`) at the panel's 128 x 64, onto one sheet (`docs/developments_plans/ADR-010-lvgl/mockups/`); `tools\ui_mock\parity_12864.py` draws the menu as gate 6 built it (every setting the unit needs, on both the screen and the web) onto `parity_12864.png`. `tools\ui_mock\panel.py glyphs <font> <characters>` prints a font's glyphs. The skill `embedded-ui-design` says how a screen is designed.
- **Page work without a unit:** `venv\Scripts\python tests\web_test.py` serves the portal as `scripts/web_build.py` builds it (`build_web/`) at the unit's own addresses, and a recording of a unit's replies (`tests/web_test_data.json`), at http://127.0.0.1:8000/, checking each write with the client's code; `--hotspot` starts it as a unit never set up, on its own hotspot. `--record <address>` records a unit again when the API grows; the owner's Wi-Fi name, the unit's address and the networks heard are left out before it is written.
- **Firmware logic without a unit:** `venv\Scripts\python tests\host_test.py` builds the PC build (`tests/host`, ADR-006, gate 4), runs each test and ends `VERDICT PASS`. CI runs it on every build. Today's tests: the loader keeping an earlier version's settings (ADR-009, gate 2), the charge profiles' record by its own load, with the EEPROM's size as a 128 kbit chip gives it (ADR-014), and the scale's framing (ADR-017, gate 2). `tests/step2_sim.py` and `tests/calibration_sim.py` load their libraries from the same build.
  - **The PC build** is a CMake project that takes the firmware's modules by their own build files, with `ot_module()` given for the PC, into `build_host/`. Its compiler is `$CC`, else `zig cc` (which the Pico extension brings into `%USERPROFILE%\.pico-sdk`), else gcc (Linux, CI); its CMake and Ninja are those `toolchain.env` names. The PC is never a board: it has no product and turns no motor.
  - **A module that requires nothing of the chip or the RTOS is built there whole** (`HOST_MODULES` in `tests/host/CMakeLists.txt`; seven today). One that comes to include an SDK or FreeRTOS header fails the host test (`file not found`). A new module free of the chip joins that list.
  - **A module not yet free is taken in part** (`HOST_PARTS`): its headers and what they require, from its own build file, and only the sources named there. Seven today (`storage`, `charge` and `charge_profiles` with a source each; `profile`, `activity`, `events` and `leds` for their headers).
  - **The stand-ins are FreeRTOS's alone** (`tests/host/stand_ins/freertos`, three headers, with only what the files built there use): the Pico SDK's went with ADR-006's gate 7. A module built there that names `rp2_sdk` fails to configure. The Pico SDK's are to be gone at ADR-006's end: do not add to them.

## Where code goes

`src/` holds the firmware by layer, and in each layer a folder a module (ADR-006, gate 2): `src/<layer>/<module>/`.

- **The layers**, a module requiring only modules of its own layer or below: `app/` (start-up and wiring), `ui/`, `web/`, `console/`, `services/`, `drivers/` (the controller board's parts), `common/` (helpers), `platform/` (the chip: `include/` the interfaces, `rp2/` the Pico SDK's side), `boards/` (pins, the flash layout, the third-party code's settings).
- **A module's folder** holds its sources, and in `include/` the headers other modules may include. A header it keeps to itself lies beside its sources.
- **A new file** goes into the module it belongs to, and into that module's `SRCS`; a new module is a new folder in its layer (see "Modules", above).
- **The compiler holds the layout** (gate 3): a module sees only the headers of what its build file names. **The layers are held too** (gate 6): nothing requires a layer above it and nothing loops, and `tools/module_graph.py` says so. `ui/` is on top of `web/` and `console/`: the UI hands them the screen's parts (the frame, the hello, its console commands), and neither names a screen.
- `src/generated/` is made by the build. `fonts/` and `scripts/` stay at the repository's root: the PC's mock tools read them too.

**Settings in the EEPROM:**
- Each module stores one struct in its own slot (1 KB; the Wi-Fi's 2 KB, of which the loader looks in the first, `EEPROM_SLOT_SIZE`, `eeprom.h`) with `load_config` and `save_config` (`common.h`), with a CRC32: a *record*. 6 KB holds the charge profiles (ADR-014). 13 to 20 KB and 22 KB hold ADR-009's first build's records on a bench unit (`eeprom.h`): a module given them clears them first. **15 KB is kept empty for good** (ADR-014): a 128 kbit chip of this family looks at 14 address bits, so the spare slot at 31 KB would lie there. On such a chip the slots left are 0 KB (once cleared), 13 and 14 KB. The bench's Pico W reports 16 KB (2026-11-28) and may be the owner's home build with such a chip, its marking not yet read; the production units, on the Pico 2 W, should have 256 kbit (the owner, 2026-11-28). The unit says its chip's size without writing (`config_eeprom_kb`: the console's `stats`, `GET /api/v1/debug`): the same bytes read at 1 KB and at 17 KB are one chip of 16 KB.
- **Never insert, always append** (the owner, 2026-11-26: "Remember, NEVER INSERT, always append for EEPROM record. This MUST be in AGENTS.md too."). The users of every release upgrade, and a record keeps its first bytes across an update, so a new release reads what the old one wrote:
  - a new field goes at the end of its record (for a header-and-array record, at the end of each element), never in the middle;
  - an old field is never moved, removed, retyped or put to a new use;
  - an appended field does not start in the old struct's tail padding;
  - a stored enum's value is never renumbered or reused: a new one takes a value no release used. Check every release tag's header before choosing one (`git show <tag>:src/<module>.h`). Why: v1.21 stored its FA-E/EN scale driver as 9, which v2 had taken for its simulated scale; a v1.21 unit on an FA-E/EN scale updated to v2 would have run the simulated scale while the motors poured real powder. v1.21's 9 stayed, and the simulated scale went to 100.
  - **a stored field is of a fixed width** (ADR-006, gate 8): `uint8_t` to `uint32_t`, `int8_t` to `int32_t`, `float`, `bool`, `char`, a stored struct, or an enum that names its integer, C23's `typedef enum : uint8_t { ... } scale_driver_t;` (GCC and clang take it in the build's `gnu11`; a value past the integer does not compile). Never a plain enum: each compiler sizes one its own way (one byte with the Pico's, which shortens an enum to its values; an int's four with ESP-IDF's, as far as is known), and the EEPROM stays on the controller board whatever chip is put in its socket. The stored enums were given `: uint8_t` by gate 8, their names, width and values kept (the owner, 2026-11-27: "but we need to make sure the existing Pico targets are unaffected");
  - `tests/release_records.py` (CI, after the builds) finds the stored records by use: every type whose size a call of `load_config`, `load_config_layout`, `save_config`, `save_config_now` or `config_read_stored` is given, **as `sizeof(<the record's type>)`** (a variable's size fails it), and the structs inside them. It checks them and every stored enum against the latest release, the compatibility floor (below), and every stored field's type; and with `--elf` (CI gives both boards' images) each record as the compiler laid it out, from the image's DWARF (pyelftools): the release's fields where they lay then (`RELEASE_LAYOUTS`, the release's layout kept in the test), nothing appended into the release's tail padding but the three known (`KNOWN_FILLER`), and both compilers' layouts the same (ADR-017, gate 1). A new release: its table printed by `--print-layouts <its ELF>`.
- The struct's layout is the stored format. **Where every change since a version was an append, `load_config` reads that version's records, both ways, with nothing to write for it:** it is the one migration, for every module (the owner, 2026-11-25 and 26): a record whose CRC32 fails at its size is looked for at each size it could have had within its slot, an earlier version's (shorter) or a later one's (longer); found, what it holds of each field is kept, element by element, the rest takes the defaults, and it is stored at this version's size at once (a later version's fields discarded), held on an update's trial as any write is. An array record declares its layout (`load_config_layout`: header, element, count). A CRC proves the bytes are whole, not what they mean: **a record whose history had an insertion would be read shifted** below the size it has been append-only from. One has: the charge record, v1.19 inserting `coarse_stop_gate_ratio` and v2.0.0 the three backoff fields (ADR-009's review, B1). Such a record declares it in its layout (`config_layout_t`'s `append_only_from` and `past`): below that size only its known earlier layouts are read, each field by field from where it lay then (`src/services/charge/charge_mode_layout.c`: v1.21's 52 bytes); any other shorter record gets the defaults. **An upgrade is always from a release to a release** (the owner, 2026-11-28: "The upgrade should be always from release to release"; 2026-11-26: "Legacy compatibility is not your concern"): the compatibility floor is the latest release, the tag `tests/release_records.py` names. A pre-release is a candidate, not a release: nothing is kept compatible with a unit on one. **A record's first two bytes are 0** (its revision before v1.17): `load_config` reads no record whose first two are not; a unit from before v1.17 is restored from a backup of its v1 web page (the owner, 2026-11-28). Going back to a version from before this loader (by USB) resets every record that grew, as before. **A field that fits in the struct's filler** keeps the size, and reads whatever byte was stored there (ADR-006, handed on by ADR-010): `release_records.py --elf` fails on one appended into the release's tail padding. Check the size before and after (`arm-none-eabi-gdb -batch -ex "p sizeof(<type>)" build/app.elf`). `tests/host_test.py` checks the migration both ways, with v1.21's powders and charge record among them. **`tests/release_records.py`** (CI runs it) checks every stored record and stored enum against the latest release: each record's fields at that release first in today's (or a layout of its history declared), each enum value meaning what it meant, each field of a fixed width; a new record is found by its use.
- **A load never writes, and never stops a module starting** (ADR-017, gate 1). It fills the defaults, then says what it found (`config_found_t`, `common.h`): read; another version's (stored at this version's size, the migration above); a save the power cut short (finished from the spare slot); blank, its first two bytes `0xFFFF` (its defaults stored, silently: a new unit, a new record's slot, the chip after an erase). Anything else, damaged, read two ways (the bus), or the EEPROM not answering, leaves the chip as it is and the module on its defaults until the person stores that module or resets the unit: its resource reads as not stored, and the main menu's first row, "Faults at the start", names it. With no EEPROM a charge and a calibration are refused (`409 no_storage`). No module's start returns early at its load.
- **A save is whole or not at all:** the record goes first into the spare slot (1 KB at 31 KB, `EEPROM_SPARE_BASE_ADDR`), then into its place, each written and read back, under the EEPROM's lock (recursive, `eeprom_lock`) held across the whole save; a place cut short, or one that did not take its write, is finished from the spare before any save writes over it, and a save is refused rather than lose that copy. A save so takes twice the writes. The erase is refused on an update's trial and holds the EEPROM's lock to the restart. The storage's buffers come from the FreeRTOS heap, not the C heap (some 3.3 KB on the Pico W, whose `malloc` panics when it runs out).
- **A settings write by name ignores a name the resource does not have, and says so:** the API's reply ends with `"ignored": [...]`, the console gives an `@ignored <name>` line; so a copy of a later version's settings restores onto an earlier one (the owner, 2026-11-26: "ignore and discard the unknown fields by name"). An action's body still refuses an unknown field (400 `unknown_field`), and so does a write from the firmware's own code: an action does what it was asked or nothing, and a name the firmware does not have is its own mistake.
- Never change a stored struct's layout without saying so in the ADR. The owner, 2026-11-26: "No firmware is released yet so no backward compatibility needed to be considered for any change within ADR-009"; a unit still upgrades from the latest release, whose every record is read by the migration above (the charge record through its declared layout).
- **Each setting is described once,** in its module's table (`settings.h`; charge mode's and the display's in a C file beside their C++ one): name, type, unit, limits or choices, when it applies, a line on what it is, and where it lies in the struct. A new setting goes in the struct and the table, and the API, the export, the schema, the portal's form (by its field's name) and the console's `setting` follow. `saved` is the struct's CRC against what was last stored, so a write from the menu counts; for a resource that shares its record (a powder of the eight, a motor of the two) it is its own part against what the EEPROM holds of it, read only when the record is not stored (ADR-008, gate 2). Each resource names where its part lies in the EEPROM (`addr`) and its revert (`revert_path`); what its block holds beside its parts (the charge profiles' choice, in their header) is put back by its own call (`revert_rest`).

**Our own code is C** (ADR-006, gates 5 and 7): no C++ of ours is left. New code is C. A file that moves from C++ to C can change meaning with no error: `abs()` of a float became the integer's (it is `fabsf` now), so compare what each function calls before and after.

**Style:** the skills in `.agents/skills`:
- `c-style` for all C and C++;
- `py-style` and `python-venv` for host tools;
- `embedded-ui-design` for anything on the unit's screen: its fonts, grid, kinds of screen and wording, and mock-ups before code.
- `web-ui-design` for anything on the web pages (ADR-008): layout by width, targets for gloved fingers, colour only where it means something, forms, confirmations, the captive-portal sheet; the mock on the stand-in before the unit.

## Proving a change on a unit

Changes are proven on a real unit, not only built. The usual proof, after a build: `rc_run.py flash`, then `rc_run.py menu_tour --compare tests/menu_baseline/<board>` (the unit's own), then `rc_run.py charge_cycle`. Each must end `VERDICT PASS`. A change meant to alter a screen updates the baseline in the same commit, with `--save`.

- **One unit is enough for a change in the application layer** (the owner, 2026-11-15: "We don't need to repeat on Pico W for application layer changes"). Read here as:
  - a change that touches nothing the two boards differ in (the modes, the control loop, the menu's logic, the profiles) is proven on whichever unit is on the probe;
  - a change to a driver, the PIO, timing against the chip, memory, the network or the build is proven on both;
  - except memory and the network once they are proven on the Pico W, the tighter of the two in RAM and speed (the owner, 2026-11-17, skipping the Pico 2 W's run of ADR-010's gate 5: "If we have verified the function on Pico W then Pico 2W is lower risk target"). Code of the RP2350's own (its slots, its PIO, its timing) is still proven on the Pico 2 W.

- **The bench rules** hold for every way of reaching a unit, the tools below included:
  - No contact with the hardware (no flashing, no serial port, no debug probe, no call to a unit over the network) until the owner says the bench is ready. Ask again in every new session.
  - An agent's run assumes the hopper is empty. The owner says when there is powder in it.
  - The motors may turn in an agent's run.
  - **The cup is checked by the tools** (the owner, 2026-11-23: the hopper stays filled). A simulated charge, a purge and `pulses` pour real powder. Every `rc_run.py` command that can turn a motor, and `tools/charge_sim/bench/record.py` with the bench tools on it, reads the real scale first, refuses a run whose most pour would take the cup past 600 gr (`VERDICT FAIL cup: ...`), reads it again after, and writes both into `logs/adr009/cup_ledger.csv`. Each run's most is computed from its own figures at 12 gr a turn (`cup_most` in `rc_run.py`; `pulses` 372 gr; a `send`'s motor line from its pauses until its stop; a `send`'s `calibrate scale` or `calibrate powder` by its method's own turns, `turns_most` in `tools/charge_sim/calibration.py` (355 and 307 gr), and its `calibrate pour <turns>` by its turns, at most the 0.5 the unit takes). The firmware bounds no motor the console turns, by design (test code stays on the PC): each tool stops what it turned, and `rc_run.py` stops both motors at every session's end, however it ended. A drop in the reading between runs is carried, never taken as the cup emptied without the owner's word (`--cup-emptied "<words>"`). `--most-pour` overrides the most, and `--no-cup-check <reason>` runs with no reading, logged. A new command that turns a motor gets its most in the same commit.
  - **A debug image goes onto a unit by the probe** (`rc_run.py flash`), never by an update (the owner, 2026-11-17).
  - **An update test never fetches from GitHub's releases** (the owner, 2026-11-17: they are not to be hammered). The unit's poll and download, and `rc_run.py update`, take their manifest and image from a local OTA server on the PC.
    - **That server is `tools/ota_server.py`.** Run `--make-certs --host <this PC's address>` once; it then serves `logs/ota_server/releases/<tag>/` (one release folder each) in GitHub's layout:
      - over HTTP (8080) and HTTPS (8443);
      - each download redirected to an asset host (8081 and 8444), with test chains of GitHub's two kinds;
      - every request printed.
      - GitHub's list of releases, `/api/v3/repos/<owner>/<repo>/releases`, for the beta channel; a release folder holding a file named `prerelease` is a pre-release, listed but never the latest.
    - **A unit trusts its test roots** only in a build that names them: `-DHTTPS_TEST_CA=ON` (ADR-010, gate 5).
    - **The server is the bench host** (ADR-010, gate 6, step 9): while it runs it announces `opentrickler-update.local` by mDNS, and every unit on the network asks it before its stored source, as the Open Weapon Mount Computer's units ask its `ota_host.py`. Nothing is set on a unit; the offer page says "From the bench host <address>". So **never leave it running while the owner tries an update from GitHub**: it takes over every unit's poll. `--no-announce` serves without the name, for a unit pointed at it by its stored source.
    - **The bench's units also store the local OTA server as their update source** (`setting settings/update source=http://<this PC>:8080/a/b`, then `save`), so a start with the server stopped still never polls GitHub. A factory reset puts GitHub's back: store it again.
    - **The test releases of ADR-010's gate 5** (v9.0.0, which confirms itself, and v9.0.1, a pre-release that never does) are kept in `logs/adr010/gate5_releases/`, out of the served folder: served, every unit would be offered them and its main menu would differ from its baseline.
- **The bench** (2026-11-14): a Pico W on the motor board with an A&D FX-300i scale, reached only by a Raspberry Pi debugprobe on SWD. Its USB port is not connected.
  - Its controller board may be the owner's home build with a 128 kbit EEPROM (the owner, 2026-11-28: "this MIGHT be my home build, for which ran 128Kbit EEPROM"): the unit reports `eeprom_kb=16` (ADR-014). So what is proven on it is proven on the smaller chip, and its spare slot lies at 15 KB.
  - A second unit, a Pico 2 W on a controller board of its own, with its own EEPROM and so its own settings, is put on the probe when the owner is asked. One unit at a time. `rc_run.py --board pico2_w` drives it. Its menu baseline was saved whole on 2026-11-19 (ADR-008), which was ADR-010's last check on it: compare against it, and save it again only with a change meant to alter a screen. ADR-009's review's three pages (`settings/calibration`, `settings/calibration/powder`, `calibration/discard`) and ADR-017's `start_faults` (the start's notice, its title alone on a unit with no fault) were saved into it on 2026-11-28, with the A&D on it; ADR-014's Charge page that evening, without it. - **The web has little memory.** A socket copies every byte it sends into lwIP's heap and holds it there until the client acknowledges it, and so does every TCP connection lwIP keeps, those the server has closed included. So the heap (40,960 bytes) is sized for lwIP's 12 connections with a send buffer of 2 segments each, and taken from the FreeRTOS heap (112 KB). On lwIP's own file server the Pico examples' 4,000 bytes ran out 7,404 times in a ten-minute soak and missed 8.9% of the web's reads (ADR-003, gate 1); on sockets, 16 KB ran out 340 times under a tuning session's load, 24 KB 54 times (gate 2). The most used moves with the Wi-Fi. A change to the server is soaked, with `--load` where it touches what a stream sends, and `net` says what it takes.
- **A GET changes nothing** (api_v1.md): read a unit over the web freely. A unit with a firmware from before ADR-003's gate 4 still has the old `/rest/` paths, which do change it (a GET of `/rest/profile_config?pf=N` selects profile N): read such a unit through the console, and copy its settings with an `rc_run.py` of its own time (below).
- **Flashing a unit can change its settings.** A record of another version is read by the migration and stored at this version's size; one this version cannot read is left on the chip, its module on its defaults, and named on the screen (ADR-017, gate 1); an older firmware from before that resets what it cannot read. Copy the unit's settings before the first flash of a newer or older version.
- **The console** (ADR-001, step 3) is stdio over RTT: the debug probe reads it from the chip's RAM, with no pin and no cable to the unit. Lines starting with `@` belong to the remote control; everything else is the firmware's log.
- **`tools/remote_control/rc_run.py`** (run with the venv's Python) starts openocd itself, keeps each session in `logs/rc/`, and ends with `VERDICT PASS` or `VERDICT FAIL <reasons>`, exiting 0 or 1. It does not start while another openocd holds its Tcl port, which would take its commands; a run that raises fails with its traceback in the log and stops its openocd:

  - `flash [--elf <path>]`: write, verify, start, check the version;

  - `watch <seconds>`: log the console for a time;
  - `snap`: the screen as a PNG under `logs/rc/snaps/`, as a person at the unit sees it;

  - `reach`: every element of every screen reached by turning alone (ADR-010, gate 6): each page by its id, each screen a row opens (a click, then Back), the dialogs, a simulated charge's screen while it zeroes and between throws (then the page its Change opens), and a cleanup's at speed 0, each turned to its top and down a detent at a time. It fails on a "<" title, a row that acts, a notes' button, a softkey or a digit of the target never reached. It reads `screen`'s marks: `back` on `@screen` (the title is Back), `info` on a `@row` only to read;
  - `charge_cycle [--target 30]`: a charge from zero to cup return and the start of the next one, with main's simulated scale switched on for the run (`sim on`), never stored. Its start writes the target into the chosen charge profile, live (ADR-014): every `rc_run.py` command that starts a charge with a target puts back what is stored after it (`setting charge_profiles/0 revert`), so the unit's settings and its Charge page are left as they were found;
  - `pulses`: whether the step pulses stop on a probe reset, an assert and a hard fault. All three are judged. It needs the two test images, built with `-DRC_TEST_FAULT=1` and `=2` into `build_w_fault1` and `build_w_fault2` (`build_2w_fault1` and `2` for the Pico 2 W, given with `--assert-elf` and `--hardfault-elf`);
  - `settings --host <address> [--save <folder>] [--compare <folder>] [--restore <folder>]`: `--restore` writes a copy back, each resource whole and stored, then compares (after a factory reset: the Wi-Fi's key is never in a copy, so the one stored stays; ADR-008, gate 4). Otherwise: the stored settings copied over the web API (`GET /api/v1/settings`, which changes nothing) and compared with an earlier copy, a field at a time; the firmware's version is reported, not judged. Take one before every flash of another version. Copies made before ADR-003's gate 3 are of the old paths and do not compare: the Pico W's v1 copy is `logs/adr003/picow/before_gate3_v1/`. A unit still on such a firmware is copied with the `rc_run.py` of a commit before gate 3 (`git show <commit>:tools/remote_control/rc_run.py`);
  - `api_check --host <address>`: the API by the client (`unit_api.py`): every GET path the index lists read twice, each answer checked against the schema's tables and the two the same, the settings and the event log unchanged; then every action the schema lists called where it is safe, each answered as api_v1.md says, a charge and a purge started and stopped with their events (the simulated scale on for it), and last a restart, after which the boot is new. It fails on an action it did not call (ADR-003, gate 4); run it with the local OTA server up (`tools/ota_server.py --no-announce`, for a unit whose stored source is this PC) and with nothing changed live on the unit: it asks a poll, and on a stopped server the poll hangs some 18 s and the check's next read timed out; a setting left changed and not stored makes it skip the saves and fail on the settings after its restart (both met 2026-11-27);
  - `stream_check --host <address>`: the event stream's life cycle (ADR-008, gate 2), stage by stage: its start (the unit, then the state), an event with its id, a reconnect from its last id with nothing missed, one whose event is no longer kept read afresh, the live weight within a second, the state again after 15 s quiet, the cap (a fourth refused 503 with `Retry-After`), a client that stops reading closed by the stall limit with lwIP's heap given back, a Wi-Fi leave and a restart (the leave leaves the old stream silent, the restart closes it; the reconnect goes on after the leave and starts afresh after the restart). It restarts the unit;
  - `settings_roundtrip --host <address>`: every setting written back as read and read again, unchanged; each field given a value outside its limits, refused, the resource unchanged; a write to the charge's and the motors' settings during a throw refused with 409. Nothing on the unit changes (ADR-003, gate 3);
  - `soak <seconds> --host <address>`: charges back to back with the simulated scale while two browsers use the web pages (the mirror, the charge page's polling, the portal reloaded, the settings read). It fails on a failed charge, on memory that is not given back (the FreeRTOS heap read quiet before and after), on an allocation lwIP's heap or a pool failed during the run (`net`, read at its start and end), on a late feed of the step pulses (`motor`), and on web reads missed past `--max-miss-share` and `--max-miss-run`; it sums the misses by kind (timeout, reset, refused, wrong). It is not part of every proof: whether a change needs one, how long, and against what limits is decided for that change, for the area it touches. Its web figures compare only when nothing else uses the unit's web pages: a browser left open on the unit tripled the timeouts of ADR-011's step-3 soak. Each poller's reply times are given (median, 95%, longest). A soak of 600 s reckons its most pour at 1,500 gr, past the cup's 600, and is refused: with the hopper empty by the owner's word it runs with `--most-pour 250`, the cup still read before and after. `--load` adds what a tuning session asks of the unit: a reply the size of a throw's samples (600 rows of 16 numbers, `/api/v1/debug/load`) pulled back to back, and a client reading the charge four times a second. `--stream` has each browser follow the event stream (ADR-008, gate 2) in place of polling the charge, each judged as a follower is: every event, no gap, no reconnect read afresh. `--upload` adds ADR-004's image: 700 KB sent back to back as a body taken in pieces (`PUT /api/v1/debug/upload`), each checked by its CRC-32. Two clients follow the event log with held reads through every soak, and it fails when either misses an event or they differ;
  - `web_robust --host <address>`: requests that are wrong or awkward (headers of 8 KB, a request line too long, another `Host`, a body longer than it says, a chunked body, a client that stops reading, writes that are not JSON or not the resource's...), each answered or closed as api_v1.md says, then seven clients at once, the parked requests and two stalls; the unit must go on answering after each (ADR-003, gates 2 and 3);
  - `scale_frames [--idle s] [--handovers n] [--reboots n] [--motors s]`: the scale's frames through the tap, summed up by phase: how many read as a number, the texts of those that did not, the time between frames (ADR-013);
  - `charge_fault <bad|quiet|purge|none> --host <address> --expect seen|not-seen`: a simulated charge with one fault put in at a weight, `state` read every 50 ms, and the charge's own `Charge: ...` lines checked with `--want` and `--want-none` (ADR-013).
  - `slot_trial --image <elf> --expect confirmed|back|refused [--corrupt]`: an image written into the free slot through the probe and tried (`update try`), no network (ADR-004, gate 1). The session's `--elf` is the image the unit runs, its update image's is `--image`: each image's console is found where its own ELF says;
  - `update --host <address> --manifest <manifest.json> [--expect confirmed|back|refused|cut|busy|second] [--refused-code <code>] [--browsers] [--new-elf <elf>]`: an update through the API from a release's manifest, the unit followed through its restart and judged by the image sent; `back` also has a start during the trial refused, `second` a second upload while the first is open; `power-upload` and `power-trial` cut the power by the probe (both cores halted, the scratch registers a power cut clears set to zero, the chip restarted) half-way through the upload, or while the image sent runs on trial, which must be one that never confirms itself; `--browsers` has two browsers on the pages during the upload (ADR-004, gate 2). Test images: `-DRC_TEST_BLOCK_VERSION=<first;second>` (a block version of its own), `-DRC_TEST_NO_CONFIRM=ON` (never confirms), `-DRC_TEST_HANG_AT_START=ON` (hangs at its first line: only the boot's own watchdog ends its trial), `-DRC_TEST_WIFI_FIRST_JOIN_FAILS=ON` (the start's Wi-Fi join skipped), `-DRC_TEST_RADIO_FAILS=ON` (the radio's start skipped: the unit runs without the network, a scan and a leave refused, "No radio" on the Wi-Fi page; ADR-006, gate 10, ADR-017). The settings' storage when it fails (ADR-017, gate 1): `-DRC_TEST_EEPROM_ABSENT=ON` (the chip looked for where none answers), `I2C_HELD_LOW` (the bus's data line driven low by its pad), `RECORD_DAMAGED` (the charge's record read with a byte wrong, the chip untouched), `SAVE_CUT` (a person's save of the powders cut by a restart after three pages of its place), `SCALE_MAKE_UNKNOWN` (make 55 stored at the start). A unit updated from v1.21 (ADR-014): v1.21's Pico W image (`C:/workspace/OpenTrickler-v1.21/build_pico_w/app.elf`) written by openocd's `program`, given values through its `/rest/` paths (a GET there changes the unit), then the full install of `-DRC_TEST_LOADS_BLANK=ON` (the loads' slot and the spare slot made blank at the start, as on such a unit: a bench unit that has run a version with loads holds them), the unit's own settings restored after.
- Console commands to drive the menu (ADR-010): `press <cw|ccw|enc|rst> [n]` (`enc` a click, `rst` Back; no long press); `screen` (what is on screen, in words: its id, kind (list, dialog, notes, edit, job, control, code), title, focus and marks (`back` when the title is Back), then a list's `@row` lines (`opens`, `editing`, `chosen` for a choice's current option, `info` for a row only to read), a card's, a dialog's or notes' `@line` lines and `@button`, the code's `@code` text (the set-up's: the hotspot's name and key) and its lines, the editor's or a job's `@figure` line (`editing` while a digit is being set), and `@softkeys` (`focus=left|right`, the one a click does); its reply gives LVGL's heap, the most used and the least free in one piece since the start), `screen list` (every page's id) and `screen <id>` (open a page, pressing nothing). `knob`: the knob's tap, taken and cleared: every edge of its button (`d` a press taken, `u` its release, `X` and `x` a bounce dropped) and each turn sent (`r`, `l`), with its time in microseconds, and `q` for an event the menu's queue had no room for.
- Console command for the settings (ADR-003, gate 3): `setting` lists the resources; `setting <path>` gives each field as an `@setting name=value` line; `setting <path> name=value ...` writes first, through the same tables, checks and refusals as the API (`@err <code> <field> <message>`); `setting <path> save` stores it, `setting <path> revert` puts back what is stored (ADR-008, gate 2). The path as the API's, with or without `/api/v1/` (`setting settings/charge`, `setting powder_profiles/3`, `setting charge_profiles/3`). A write is live, not stored, until saved; the Wi-Fi key is written but never shown.
- Console command for the network (ADR-003): `net`, lwIP's heap and the pools a web connection takes from (TCP connections, segments, pbufs, receive buffers), each in use, most ever, size and failed allocations, and the event streams open, opened and refused (`live`, `live_opened`, `live_refused`; ADR-008, gate 2). The heap is 40,960 bytes (ADR-003, gate 2); a change to the server is measured with it. `tcp_pcb` at 12 of 12 is no fault: closed connections wait out TIME_WAIT there and lwIP takes back the oldest for a new one, counting a failure only when none can be taken (`tcp_alloc`). `GET /api/v1/debug` gives the same over the web, with the server's own counts. **An item of a streamed reply must fit a chunk** (1,526 bytes: the index's guide, a schema's action): longer, the reply is cut off there, "HTTP: a streamed reply overflowed its chunk", and only a unit shows it. The guide is held by a static assert (`api_v1.c`; ADR-014 met it on the Pico W, the index cut off for every client). `net log on|off` (never stored) puts each connection and request on the console, with the client's address and the unit's time: a client's link read by its own reads (ADR-008, gate 4). Always on the console: each reply of 400 or more in the unit's own words, a request dropped or reset, and the slots all held.
- Console commands for updates (ADR-004): `update` (the slot running, whether on trial, the free slot, the job), `update try` (a trial of the free slot's image, once it is checked), `wifi leave` (the station leaves its network, as when its router goes away; it joins again within a minute). `wifi scan` (the set-up's scan, waited for: `@scan` lines, each network by name, strongest first) and `wifi join` (the stored network with its stored key, through the set-up's join: only while the unit is its own hotspot, which stays up; the end in `GET /api/v1/network`'s `station`) (ADR-008, gate 4). A probe build, `-DRC_TEST_AP_PROBE=ON` (ADR-008, gate 1), starts as its own access point and never retries its network by itself. ADR-010's poll: `update check` (a poll now), `update poll` (how the last poll went, and what its fetch took). A download logs what it took (`Update: downloaded ...`) and the job task's stack at install, before the restart wipes them.
- Console command for the tasks: `stats tasks` gives each task's stack never touched (`@task` lines) before the `stats` reply. The job task's and the poll's stacks were sized from it (ADR-010, gate 5).
- Console commands for the motors and charging: `motor <coarse|fine> <rev/s>`, `motor` alone (the steps counted on each STEP pin, the steps fed, the feeds that came late, with the unit's clock: two replies give a speed), `sim on|off`, `charge <gr>` (a start through the same entry point as the API's, `by` console: it writes the target into the chosen charge profile, live, not stored; ADR-014), `charge stop`. `stats` ends with the charge controller's cost since the start: `charge_tick_us` and `charge_reading_us` (most/mean) and `charge_heap_low`, then `eeprom_kb`, the EEPROM's size told without writing (32, 16, or 0 when it cannot be told; ADR-014).
- Console commands for the motor drivers (ADR-012): `tmc <coarse|fine>` (the driver's registers by field as `@tmc` lines, then its serial line's counts), `tmc <coarse|fine> setup <n>` (set up n times from the stored settings), and, never stored, `tmc <coarse|fine> lose` and `find` (the driver made to look absent, and found again) and `tmc <coarse|fine> fault <short|hot|reset|supply|none>` (the driver read to report a fault). `state` ends with `drivers=<coarse>,<fine>`: what each driver was last found to be.
- Console commands for the scale, never stored (ADR-013): `scale tap on|off` (every make's frames as `@sf` lines, ADR-017, gate 2), `sim bad` (the simulated scale's next reading does not parse), `sim quiet <ms>` (it sends nothing for that long), `sim rate <per second>`, `sim weight <a number|off>` (it shows that weight, whatever its powder does). `stats` counts `bad_frames`.
- It counts as failures: a line with `assertion` or `PANIC`, no reply within 5 s, an `@err` reply, `up=` going backwards unasked, and a core found halted (named with its function).

## Decisions and ADRs

Work is planned and recorded as architecture decision records in [docs/developments_plans](docs/developments_plans/README.md). The process is in that README. The parts that trip people up:
- **Approval first:** an ADR is approved by the owner before work starts.
- **One at a time:** one ADR is open at a time; a functional change and a dependency update are never mixed in one.
- **Plain form:** plain words. What we want, the owner's direction, what we know (measured or checked in the code), what we do, how the unit shows it works. `progress.md` records what was built and measured.
- **Close before the PR:** an ADR is closed (Built, in its README, its progress and the index) in its branch before its PR is opened.
- **Stage gates, not small ADRs** (the owner, 2026-11-15: "Don't use small ADR. If you need staged release, you can have smaller stage gates within ADR-003"). A large ADR is built in gates inside it. A gate is approved and built on its own and may be merged by a PR of its own; the ADR is then Open until its last gate, which closes it before its PR.
- **PRs from others** are not merged as they stand. Each is discussed with the owner first (ADR-002).
- **A change to the ADRs goes straight to main** (the owner, 2026-11-17: "For ADR change you don't need PR, just merge to main directly"). Read here as: a change to the plans alone (an ADR drafted or revised, an answer of the owner's written in, the order, the handover, and the rules of this file that come with them) is committed on a branch, merged into main and pushed once, with no PR. An ADR's built work still goes by its PR.
- **An update that is not a feature may be merged without asking** (the owner, 2026-11-13: "for no feature update you can just merge the code"). Read here as: a change that leaves what the firmware does for a user as it was, such as CI, build scripts, host tools and documents. Open its PR, see its checks, merge it. A feature, or anything a user can see, waits for the owner.
- **Push only when it is needed** (the owner, 2026-11-15: GitHub has begun to block accounts that agents push from often, and the owner's must not become one). Read here as:
  - commit locally as often as the work needs; a local commit never reaches GitHub;
  - push a branch when its work is ready for its PR, or when the owner asks to see it on GitHub. Not after each commit, and not to keep work in progress safe;
  - once a PR is open, gather its fixes and push them together;
  - never push to try something in CI. CI builds with the toolchain a PC builds with, so a local build answers first.

## Do not

- **Do not edit `src/generated/`.** Change the source (a page, a `.pio` file, `scripts/gen_version.py`) and build.
- **Do not change anything under `library/`.** It is third-party code in submodules.
- **Do not change a stored struct's layout without saying so in the ADR** (see "Settings in the EEPROM").
- **NEVER INSERT a field into an EEPROM record: always append** (the owner, 2026-11-26), and never renumber or reuse a stored enum's value (see "Settings in the EEPROM").
- **Do not push often.** Push when a branch is ready for its PR, not as you go (see "Decisions and ADRs").
- **Do not merge a feature, close a PR or an issue of someone else's, or post a comment** without the owner's word. An update that is not a feature is the exception above.
